## 1. 结论摘要

**总体判断：架构方向正确、工程纪律好，但规模已经超出当前验证能力，并且有几处设计层面的问题需要在继续堆功能之前解决。**

- 这是一个 5 天内（09-28 → 10-02）由 AI 生成的约 **14.5 万行**代码基：后端 Python 7.3 万行、前端 4.5 万行、测试 2.6 万行、浏览器验收脚本 1.4 万行；106 次提交中 97 次由 Claude 署名。
- 多租户隔离、消息可靠性、密钥管理、可观测性这几个 SaaS 的"硬骨头"做得扎实，有自动化测试兜底。
- 但"模块化单体"已经退化成一个 26 个模块互相依赖的大泥球；自研的"接口传输加密"收益低、代价高；文件下载链接长期有效且不校验访问者；调度进程把 CPU 密集和阻塞 IO 放在同一个事件循环里；性能目标从未被测量过。
- 建议：**先止血（4 项，1–2 周），再花 1–2 个月还架构债，之后才继续加渠道和功能。**

## 3. 做得好的地方（应当保留）

1. **租户隔离是真的"四层防护"。** 每张带 `tenant_id` 的表都 `ENABLE + FORCE ROW LEVEL SECURITY`，并有测试直接查 `pg_class` 断言没有漏网之表（`tests/test_rls.py:140`）；租户表之间一律用 `(tenant_id, id)` 复合外键，外键检查绕不过租户；`app_current_tenant()` 用事务级 `set_config`，SQLAlchemy 在每个新事务 `after_begin` 时重设（`app/db/session.py:46`）；越权矩阵测试枚举每一个带路径参数的接口并有覆盖检查（`tests/test_authz_matrix.py`）。
2. **消息链路的可靠性设计完整。** `(channel_account_id, channel_msg_id)` 幂等入库、按 seq 对账补漏、IM 操作走发件箱与状态变化同事务提交、Redis Streams 按租户分流 + 分区租约 + XAUTOCLAIM 接管 + 死信流（`app/events/bus.py`）。
3. **密钥与凭证管理超出一般水平。** 租户级信封加密、可轮换、盲索引不随轮换改变、注销时加密擦除（`app/modules/security/keys.py`）；生产环境启动时拒绝任何开发默认密钥（`app/core/config.py:_check_prod`）；接口密钥只存哈希、常量时间比较；刷新令牌家族轮换与撤销。
4. **可观测性做到了"带租户维度"。** 指标、链路、JSON 日志都带 tenant；32 条告警规则有 promtool 单测；每个调度任务有执行次数、耗时、最近成功时间。
5. **工程纪律。** 严格 mypy、ruff 全家桶、ESLint、OpenAPI 导出与前端类型生成在 CI 里做漂移检查；金额一律 `Numeric(12,2)` / `Decimal`；全库没有一处 naive datetime、没有 `time.sleep`、没有裸 `except`；迁移是手写 SQL 且每个都有 `downgrade`。
6. **有自查意识。** 实施计划 §28 记录了一次全面检查并修了 7 个问题（上传签名、`X-Forwarded-For` 信任、点击劫持等）。

## 4. 问题清单（按严重程度）

### P0 · 设计层面，建议立刻决策

#### 4.1 "模块化单体"已经退化为大泥球

**证据**
- 29 个模块之间有 254 条跨模块 import 边，**57 对互相引用**；26 个模块落在同一个强连通分量里，即从任意一个模块出发都能走回自己。
- `orders` 引用 18 个其他模块、`todos` 17 个、`ai` 16 个、`wecom` 13 个。
- `main.py:9` 必须 `import app.db.models` 把全部模型先注册一遍，ORM 才能解析跨模块外键；`history/service.py:58` 用 `importlib.import_module` 延迟导入来躲循环依赖。
- 设计文档 D1 明确写着"模块之间只通过服务接口和领域事件交互，日后可以把渠道适配器、AI 推理拆成独立服务"——目前做不到。

**影响**
- 任何一处改动都会沿着循环传播，无法对单个模块做隔离测试，新人无法从一个模块读起。
- 设计里保留的"拆服务"演进路径已经关闭。
- `history` 的 `importlib` 技巧说明作者已经撞上了循环导入，并选择绕过而不是解耦。

**建议**
- 先用 `import-linter` 写下分层契约（例如 `core → tenancy/iam → channels/conversation/sessions → ai/kb → orders/todos/warehouse/formkb → reports`），让 CI 阻止新的反向依赖；存量违规列入白名单逐步清零。
- 跨模块的"反应式"逻辑（会话结束后解析待办、订单确认后通知、领料单确认后学习表单知识）改为发布领域事件，由各自模块订阅，而不是直接 import 对方的 service。
- 每个模块只通过 `__init__.py` 暴露公共接口，禁止 `from app.modules.x.models import ...` 跨模块引用 ORM 模型（报表、导出等确实需要跨模型的，放到专门的 `reports` / `export` 读模型层）。

#### 4.2 自研"接口传输加密"（§25.15）成本高、收益低

**它做了什么**：浏览器和后端做 ECDH 握手（服务端用内置公钥签名），之后每个 `/api/` 请求的头、查询串、请求体用 AES-GCM 加密，响应整体加密；Redis 记录 nonce 防重放（`app/modules/transport/*`、`packages/api-client/src/transport.ts`，两边各 ~400 行）。

**威胁模型站不住**
- 做加密的 JS 和公钥都是经同一条 TLS 通道下发的。能在 TLS 上做中间人的攻击者，同样能改掉下发的 JS（跳过加密、把密钥发回去）。构建时写死公钥并不改变这一点，因为校验公钥的代码也在被下发的 JS 里。
- 它真正能挡住的只有"能解 TLS 但只记录不篡改"的被动代理（例如企业出口的审计网关）。这是一个很窄的场景。
- README 自己也承认它不能防止用户在自己浏览器里查看数据。

**代价是实打实的**
- 响应必须收齐后整体加密（`middleware.py:_SealingSend`），所以**没有流式响应**：导出 ZIP、SSE 都做不了，大响应全在内存里；请求体上限 64 MB 也是整体读进内存。
- 每个请求多一次 Redis 往返登记 nonce；握手失败、428/426 重试、时钟偏差 5 分钟拒绝（用户电脑时间不准就打不开系统）。
- 抓包、curl、API 网关缓存、CDN、浏览器 DevTools 全部失效，排障成本显著上升；运营后台和 Widget 也被拖进来。
- 两套实现（Python / WebCrypto）必须永远保持字节级一致。

**建议**：默认 `off`，保留为"按租户可选、需要书面说明合规依据"的高级选项；把精力放在 HSTS、CSP、证书透明度、依赖审计这些对真实威胁有效的措施上。如果确实有监管要求（例如某行业的"应用层加密"条款），把条款原文写进设计文档，再按条款范围实现。

#### 4.3 文件下载链接长期有效、不校验访问者

**证据**：`/api/v1/files/{key}?sig=`（`app/modules/files/router.py:48`）只校验 HMAC，不看谁在访问、也不看这个文件属于哪个会话；签名没有时间成分，"链接本身不过期"（`files/service.py` 模块注释）。设计文档 §13.3 原本要求"先校验数据范围，再签发短时有效的签名 URL"。实施计划 §28.4 把它列为"风险低、不改"。

**为什么不低**：平台存的是客户发来的身份证照片、合同、银行卡截图。链接会进浏览器历史、代理日志、导出文件、转发的聊天记录、邮件；一旦泄露，在保留期内（可能是几年）任何人都能打开。换 `EDP_FILE_URL_SECRET` 又会让所有历史消息里的链接同时失效（没有密钥版本）。

**建议**：下载入口要求员工令牌或访客令牌，校验能否看到该消息所在的会话，再 302 到 5 分钟有效的对象存储地址；消息里不再存可直接打开的链接，只存 `key`，前端在渲染时请求。至少给签名加上过期时间和密钥版本。

#### 4.4 开发速度与验证深度严重不匹配

**证据**
- 5 天、14.5 万行、97% 提交由 AI 署名；单次提交最多改 118 个文件。
- 全部外部集成（OpenIM、企业微信、大模型、邮箱、ClamAV、S3）都是对着同一作者写的模拟服务（`tests/fake_*.py`）验证的；OpenIM 契约测试只在设了 `EDP_TEST_OPENIM_URL` 时跑；企业微信服务商资质还没有，代开发应用、微信客服、客户联系的真实接口一次都没打通过。
- 待办、订单、加工、仓库、领料、表单知识这些业务流程的规则（谁能改价、暂欠审批、缺货处理、配方估算）没有领域专家复核的痕迹。
- 设计文档 §19.1 给出的性能目标（消息 P95 < 500 ms、AI 首响 P95 < 8 s、1 万在线访客、300 万条/天）**从未测量**，仓库里没有任何压测脚本。

**影响**：代码"看起来对、测试也绿"，但绿的是作者自己定义的世界。真实企业微信回调的字段差异、OpenIM 在网络抖动下的 seq 行为、大模型供应商的工具调用兼容性，都可能在上线后第一周集中爆发。

**建议**
- 冻结新功能，选 2–3 家种子租户走真实链路；企业微信先拿到服务商测试企业。
- 核心流程（接入 → AI → 转人工 → 转接 → 结束 → 沉淀；下单 → 审核 → 加工 → 入库 → 发货）由人逐条对照设计文档复核一遍。
- 把真实 OpenIM 契约测试放进 CI（`e2e-full` 已经起了 OpenIM，顺手跑 `EDP_TEST_OPENIM_URL`）。
- 用 k6 / Locust 对 Widget 初始化、消息回调、AI 回复各做一轮压测，拿到基线。

### P1 · 需要在下个迭代处理

#### 4.5 调度进程：35 个任务共享一个事件循环，CPU 和阻塞 IO 没有隔离

**证据**
- 设计 §6.1 画了四类进程（API、实时消费、后台任务、调度），§6.3 选了 Taskiq 做后台任务；实际只有三类，"后台任务"全部并入 `app/scheduler.py` 的 `JOBS`。
- `kb/importer.py:296` 直接调用同步的 `parsers.parse_document`（pypdf 最多 500 页、docx 50 MB 的 XML 解析），`lifecycle/export.py:220` 用同步 `zipfile` + `tempfile` 生成整租户导出，都没有 `asyncio.to_thread`。同一个循环里跑着 `session-timers`（10 s）、`transfer-timers`（5 s）、`im-ops`（5 s）、`mail-poll`（10 s）。
- API 侧 `products/router.py` 的 Excel 导入预览同样在请求里同步解析。
- 所有任务共用一把 30 s 的租约（`scheduler.py:LEASE_KEY`）：循环被长任务卡住 30 s 后租约过期，待命副本会拿到租约并开始跑**同样的任务**，而第一个副本并不知道自己已经丢了租约——账单生成、提醒发送这类任务可能重复。

**建议**：立即给解析、压缩、Excel 加 `to_thread`；中期把导入 / 导出 / 提炼 / 周报 / 专区拉取这类重任务拆到单独的 job worker，按任务分别持有租约，并把"持有租约的任务仍在运行"作为续约条件。

#### 4.6 绕过 RLS 的连接用得太广

`platform_sessionmaker`（`edp_platform` 角色，RLS 对它全放行）在应用代码里出现 **77 次、18 个模块**，既有调度任务跨租户扫描（合理），也有请求路径（`security/scanning.py:145 blocked()`、`ai/llm_router.py`、`ai/prompt_store.py`、`security/keys.py`）。每一处都要靠手写 `WHERE tenant_id = ...` 保证不串租户，RLS 这张安全网在这些地方是关着的。

**建议**：提供 `platform_tenant_session(tenant_id)`——即使用平台角色也 `set_config('app.tenant_id')`，并把 `platform_access` 策略改成"没有设置租户上下文时才全放行"；把 77 处列成清单逐个收敛。

#### 4.7 PII 脱敏的承诺大于实现

`ai/pii.py` 只用 4 条正则（手机号、身份证、银行卡、邮箱）。姓名、收货地址、座机、微信号、车牌都会原样进入大模型，而设计 §22 承诺"待办和订单包含个人信息（收货地址、电话、证件号）→ 模型只看到占位符"；`orders/ai.py` 的 `receiver_address` 直接作为工具参数往返模型。**建议**：要么把地址等字段也做占位符（结构化字段天然可做），要么在文档和隐私声明里把真实边界说清楚。

#### 4.8 性能基线与明显的低垂果实

- 每个员工请求在进入业务代码前：解 JWT → Redis 租户限流 → Redis 传输 nonce → 数据库加载 Principal（权限每次从库里读，`iam/deps.py:52`）。三次往返是固定开销，高 QPS 时会先在这里撞墙；Principal 可以按 `staff_id + 角色版本号` 缓存 30–60 s。
- 控制台 `main.ts` 全量引入 Element Plus 及其 CSS，主包 1.18 MB；改成 `unplugin-vue-components` 按需引入通常能减一半以上。
- 单一 OpenAPI 文档 2 MB、生成的 `schema.d.ts` 1.6 MB 被三个应用共用；Widget 也背着整个平台的类型。类型会被擦除不影响运行时，但说明 API 面已经很大（423 个操作），需要考虑按应用拆分文档。

#### 4.9 测试金字塔是倒的

- 后端 527 个测试几乎都是"起 FastAPI + 真实 PostgreSQL + Redis"的接口级测试：真实度高，但没有基础设施就一个都跑不了（本次就是如此），单个用例的运行成本高，也难以定位到函数级别。
- 前端 194 个单测全是纯函数（`labels`、`hours`、`scale` 等），**零组件测试**；1,124 行的 `OrderDrawer.vue`、882 行的 `ChatPanel.vue` 只有夜间 Playwright 覆盖。
- 27 个验收脚本有 37 处固定等待，依赖整套栈（OpenIM 镜像约 3 GB），只在夜里跑一次：UI 回归最早第二天才知道。

**建议**：给会话引擎、路由分配、决策引擎、价格计算这类纯逻辑补函数级单测（可以不碰数据库）；前端用 Vue Test Utils 给表单型组件补交互测试；把 P0 之外最关键的 2–3 个验收脚本（工作台、订单）提到每次推送。

#### 4.11 文档：内容过剩、结构不足

- README 约 700 行，只有"文档"和"快速开始"两个二级标题，部署、运维、各功能说明全部塞在"快速开始"下的长段落里。
- 设计文档 3,057 行、实施计划 1,902 行，都是 v0.3 → v1.3 的追加式修订；"现在是什么样"要靠读者自己合并多处修订（例如 §6 仍写着四类进程和 Taskiq）。
- 建议：README 拆成 概览 / 本地开发 / 部署 / 运维手册 / 功能导览；设计文档改为"当前状态"版本，把历史决策移到独立的 ADR 目录。

### P2 · 记录在案，择机处理

- **安全响应头**：nginx 只有 `X-Content-Type-Options` 和 `Referrer-Policy`，没有 CSP（除 `frame-ancestors`）和 HSTS（可能放在 Ingress，但仓库里没有体现）。
- **访客令牌**：`localStorage` 保存 365 天（`widget/src/visitor.ts`），嵌入第三方站点时属于可接受范围，但应写进隐私说明。
- **测试清库列表**：`conftest.ALL_TABLES` 只列了 34 张表，其余靠 `TRUNCATE tenants CASCADE` 级联；将来一张没有外键指向 `tenants` 的租户表会在测试间泄漏数据。
- **OpenIM 的双份消息**：平台库和 OpenIM 各存一份，保留期是两个独立开关（租户设置 vs `EDP_IM_RETAIN_DAYS`），文档要求人工保证"后者不长于前者"，没有自动校验。
- **许可证**：`@openim/client-sdk` 是 GPL-3.0，设计文档已标为"商用前购买授权"的上线闸门，需要有人跟进。
- **依赖审计**：`pip-audit` / `pnpm audit` 只在 §28 手工跑过一次，没有进 CI。
- **CI 成本**：每个分支的每次推送都构建两个镜像并跑 30 分钟的 P0 浏览器验收；夜间全量 150 分钟。可以把镜像构建和验收限制在 PR 与 main。
- **出站地址的 DNS 重绑定窗口**：§28.4 已记录（先解析校验、httpx 再解析一次）；生产只允许 https 并校验证书，实际风险低。
