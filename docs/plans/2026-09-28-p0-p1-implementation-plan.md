## 1. 目标

- **P0（多租户骨架）**：
  - 开发环境一键启动。
  - 平台可以开通租户；员工可以登录。
  - 按角色控制功能权限，按租户隔离数据（PostgreSQL RLS），按归属控制客户可见性（DataScope）。
  - 提供控制台和运营后台的骨架，CI 全绿。
- **P1（Web 客服核心）**：接入 OpenIM，完成访客 Widget、会话与路由、坐席工作台、转接与客户转移。P0 完成后再细化任务。

## 2. 工程约定

- **目录**：
  - `backend/`：FastAPI 后端。
  - `frontend/`：pnpm workspace，包含 `apps/console`、`apps/platform-admin`、`packages/api-client`。
  - `deploy/compose/`：开发环境。
- **后端**：
  - Python 3.12，用 uv 管理依赖。
  - FastAPI、SQLAlchemy 2（async + asyncpg）、Alembic。迁移手写，因为 RLS 策略要用 SQL 表达。
  - pydantic-settings（环境变量前缀 `EDP_`）、argon2-cffi、PyJWT、uuid-utils（UUIDv7）。
  - 测试用 pytest + httpx，代码检查用 ruff + mypy。
- **数据库角色**：

  | 角色 | 用途 | RLS |
  |---|---|---|
  | 所有者（开发环境为 `postgres`） | 执行迁移 | — |
  | `edp_app` | 员工请求（租户内） | 受租户隔离策略约束 |
  | `edp_platform` | 平台运营、租户开通 | 通过专用策略访问全部行 |

- **租户上下文**：
  - 每个事务开始时执行 `set_config('app.tenant_id', <租户ID>, true)`，由 SQLAlchemy 的 `after_begin` 事件自动完成。
  - RLS 策略使用 `app_current_tenant()`（等价于 `NULLIF(current_setting('app.tenant_id', true), '')::uuid`）。
  - 没有设置租户时查询返回空（fail-closed）。
- **跨租户引用**：租户表之间的外键使用 `(tenant_id, id)` 复合外键，从数据库层面禁止引用其他租户的行。
- **接口**：
  - `/api/v1/*` 面向租户员工，`/platform/v1/*` 面向平台运营。
  - 错误统一为 `{"error": {"code": "...", "message": "..."}}`。
- **令牌**：
  - 员工：Access Token（15 分钟）+ Refresh Token（7 天，httpOnly Cookie，每次刷新都轮换；检测到重复使用时吊销整组）。
  - 平台：独立密钥签发的 Access Token（2 小时）。
- **前端**：
  - Vue 3 + TypeScript + Vite + Pinia + Vue Router + Element Plus（中文）。
  - API 类型由后端导出的 `openapi.json` 经 openapi-typescript 生成，请求用 openapi-fetch。
- **提交**：每个任务独立提交，提交前本地跑通 lint 和测试。

## 7. P1 M1：OpenIM 集成（细化）

### 7.1 技术验证结论（OpenIM Server v3.8.3，2026-09-28 在开发环境实测）

- **开发环境**：
  - 官方镜像 `openim/openim-server:v3.8.3`，依赖 MongoDB 7、Redis 7、etcd 3.5、Kafka（KRaft 单节点）和 MinIO，启动约 20 秒后健康。
  - Docker Hub 上的 `minio/minio` 已无法拉取，开发环境暂用 `bitnamilegacy/minio:2024.1.11`；Kafka 用 `apache/kafka:3.9.1`。
- **发送后回调 `afterSendGroupMsg`**：
  - 在消息写入 Kafka 之后、分配 seq 之前触发，所以回调里的 seq 恒为 0，去重只能用 `serverMsgID`。
  - 通过进程内队列异步投递（2 个 worker，缓冲 100），失败不重试，因此对账是必需的，不是可选的兜底。
  - 平台自己发送的在线信令（自定义消息）也会回调，入库时要按发送者过滤。
  - REST 发送的消息 `msgFrom=200`，SDK 发送的为 100。`ex` 可以由客户端任意填写，不能作为身份依据。
- **建群**：
  - 只有管理员能建立群主为他人的群，但任何用户都能建立自己当群主的群。
  - 因此开启 `beforeCreateGroup` 回调，拒绝非平台服务群。回调里群主出现在 `initMemberList`（roleLevel=100），`ownerUserID` 字段为空。
- **对账接口**：
  - `/msg/get_conversations_has_read_and_max_seq` 批量获取会话最大 seq；`/msg/pull_msg_by_seq` 按区间拉取，`content` 为 base64。
  - 群通知（建群、进群、踢人）也占用 seq；在线信令不落库，不占 seq。
  - 最大 seq 与查询用户是否在群里无关；拉取消息时才按成员身份过滤。
- **ID 字符**：用户 ID 只接受字母、数字和下划线，含 "-"、"." 等字符时返回 1001。
- **错误码**：重复注册用户返回 1102，重复建群返回 1202，可以按"已存在"处理；未注册用户换 token 返回 1004（不是 1101）。
- **踢人**：成员会被移除，但接口可能返回 1001 "maxSeq is invalid"（被踢用户从未同步过该会话时）。M5 转接时以成员列表为准。
- **JS SDK**：`@openim/client-sdk` 3.8.3（GPL-3.0，上线前需要商业授权），可以直接在 Node 22 中运行，用于自动化测试。

### 7.2 约定

- **IM ID**（`{t}` 为 IM 前缀：租户代码中的 "-" 换成大写 "X"，因为 OpenIM 不接受 "-"；ID 为 32 位十六进制）：
  - 客户身份 `{t}_c_{身份ID}`、员工 `{t}_s_{员工ID}`、机器人 `{t}_bot`、系统用户 `{t}_sys`。
  - 服务群 `{t}_r_{RoomID}`，群主为 `{t}_sys`。
  - 前缀不含下划线，回调里按第一个下划线拆出前缀，再把 "X" 还原成 "-" 得到租户代码（租户代码只有小写字母，替换可逆）。
- **渠道 key**：`{t}.{32 位随机十六进制}`。公开嵌入客户网站，只用于识别渠道，不是凭证。
- **访客令牌**：平台签发的 JWT（独立密钥，audience `edp:visitor`，有效期 365 天），代表浏览器里的一个访客身份。令牌无效时按新访客处理。
- **回调地址**：`/hooks/openim/{共享密钥}/{command}`。OpenIM 回调不签名，所以把密钥放在路径里；部署时回调入口只对内网开放。

- 前端 28 个单元测试：新增 `im-client` 与 Widget 的逻辑。

**联调中发现并已修复的问题**：

- **租户代码含 "-" 时无法接入**：OpenIM 的 ID 不接受 "-"。已改为 IM 前缀编码（见 §7.2），内存版 OpenIM 和契约测试都覆盖了这条规则。
- **SDK 缺陷**：`@openim/client-sdk` 3.8.3 中，没有任何会话的用户登录后，一旦收到新会话的消息，SDK 就会抛出异常，发送也随之失败。新访客、新开通的坐席都会遇到。
  - `im-client` 已加防护；SDK 内部结构变化时测试会失败。
  - 升级 SDK 时需要重新确认；建议向 OpenIM 反馈。
- **刷新后历史为空**：SDK 登录后首次同步完成之前拉取历史，会得到空列表。`im-client` 的 `connect()` 改为等同步完成后才返回。
- **回调响应被误当作放行**：OpenIM 把回调的任何 JSON 响应都当作放行。密钥错误时改为返回纯文本，使配置错误表现为拒绝。

## 9. P1 M2：会话与路由（完成情况，2026-09-28）

### 9.1 实现要点

- **进程**：API、实时消费进程（`python -m app.worker`）、调度进程（`python -m app.scheduler`）。
  三者共用 `AppContext`（数据库、Redis、OpenIM 客户端、事件总线）。
- **事件流**：Redis Streams，按 Room 哈希到 8 个分区。
  - 每个分区由持有租约的一个消费者顺序处理，同一个 Room 的事件严格有序；可以运行多个消费进程。
  - 新的租约持有者先接管前任留下的未确认事件，再读新事件。
  - 处理失败重试 3 次，仍失败写入死信流 `edp:events:dead`，不阻塞分区。
  - 回调和对账入库的新消息发布 `message.received`；发布失败的由调度进程每 30 秒补发。
- **会话引擎**（设计 §8.2、§11.3）：
  - 客户的第一条消息开启会话，按渠道绑定的路由策略（没有绑定时用默认策略）进入排队。
  - 分配顺序：归属坐席优先 → 技能组（会话或策略的默认技能组；都没有时在全部坐席中分配）
    → 负载率（当前会话数 / 并发上限）最低 → 最久未分配。按租户加咨询锁，不会超过并发上限。
  - 分配后把坐席拉进服务群，给客户发"客服 XX 为您服务"，给坐席发 `session.assigned` 信令；
    没能立即分配时告知排队位置。
  - 结束会话时给客户发结束提示，把坐席移出服务群；空出的名额立即分给排队中的会话。
  - 调度进程每 10 秒：心跳超过 90 秒的坐席下线，其未回复过的会话退回队列（重新计时，优先级 +1）；
    排队超过 `max_wait_seconds` 转为留言；人工接待超过 `idle_close_minutes` 没有新消息则结束。
  - 非工作时间的消息直接转为留言（同一段时间内的后续消息追加到同一条留言）。
  - 所有状态变化写入 `session_events`。
- **IM 发件箱（`im_ops`）**：拉人、踢人、客户提示、坐席信令与会话状态在同一个事务里写入，
  提交后立即执行；同一个 Room 按写入顺序执行，失败的按指数退避重试（调度进程每 5 秒），
  信令失败不重试。这样 OpenIM 短暂不可用时，状态与 IM 最终一致。
- **调度进程选主**：用 Redis 租约保证只有一个实例执行周期任务（M1 后续事项"调度进程单实例"已完成）。
- **数据范围**：
  - 客户：归属自己的客户 + 当前有会话分配给自己的客户（会话结束后不再可见）；
    主管另可看到所带技能组组员名下和正在接待的客户。
  - 会话：分配给自己的、自己名下客户的；主管另可看到所带技能组及组员的会话。
- **接口**：技能组、路由策略（含工作时间校验）、渠道绑定策略、坐席看板与并发、
  坐席接待状态 / 心跳 / IM 令牌、会话列表 / 详情 / 结束、留言列表 / 完成。

## 10. P1 M4：坐席工作台（完成情况，2026-09-28）

### 10.1 联调发现：OpenIM 实时推送的两个问题

浏览器验收一开始只有约一半的运行通过：访客偶尔收不到"客服 XX 为您服务"，坐席偶尔收不到分配信令。
排查 OpenIM 源码和日志后确认是两个问题：

1. **离线推送拖慢在线推送**。默认配置启用了个推（Getui）却没有凭证。推送服务按 Kafka 分区顺序处理消息，
   每次给离线用户（例如已经关掉浏览器的坐席）推送，都要等一次失败的外部 HTTP 请求，排在后面的在线推送随之延迟。
   开发环境已关闭离线推送（`IMENV_OPENIM_PUSH_ENABLE=none`）。平台是 Web 端，不需要手机离线推送；
   以后接入 App 时再配置推送供应商，并单独评估推送服务的吞吐。
2. **刚连上的用户收不到推送**。msggateway 每秒批量上报一次用户上线，推送服务要过一两秒才知道这个用户在线。
   这段时间里发给他的在线信令直接丢弃，群消息也不推送；JS SDK 不检测 seq 缺口，之后也不会补拉。
   处理方式是把平台接口作为消息的准绳，IM 只负责低延迟：
   - Widget：连上后、之后页面可见时每 10 秒、以及重连后，用访客接口（`GET /api/v1/visitor/messages`）补齐，
     按 IM 消息 ID 与 IM 推送去重。
   - 工作台：先连 IM，等 2 秒再上线接单；会话列表和当前会话每 10 秒以接口为准刷新一次，重连后立即刷新。

修复后，M4 浏览器验收连续 5 次全部通过。

## 12. P1 M3：访客 Widget（完成情况，2026-09-28）

### 12.1 实现要点

- **嵌入**：`embed.js`（Widget 的 `public/` 下）在页面右下角放一个"在线客服"按钮，点开时显示 iframe 里的 Widget。
  父页面与 iframe 之间用 postMessage 通信，双方都校验来源：`edp:open` / `edp:hidden`（显示状态）、
  `edp:unread`（收起时收到的新消息数，显示为按钮角标）、`edp:close`（Widget 里的收起按钮）。
  iframe 默认隐藏但照常连接 IM，所以收起时也能收到消息和提醒。
- **允许嵌入的网站**（渠道设置 `allowed_origins`）：Widget 取父页面来源（`location.ancestorOrigins`，
  不支持时用 referrer）随初始化请求上报，不在列表中的返回 403"当前网站未被授权接入在线客服"；
  列表为空表示不限制；Widget 自己的地址（`EDP_WIDGET_PUBLIC_URL`，例如访客测试页）总是允许。
  这一校验用于防止别人随手把客服窗口挂到自己的网站上，不是安全边界：来源由浏览器上报，脚本可以伪造请求。
  访客身份的可信度只来自下面的签名。
- **实名访客**：渠道启用后生成签名密钥（`POST /api/v1/channels/{id}/identity-secret`，可更换）。
  网站后端计算 `HMAC-SHA256(密钥, "<external_id>:<name>:<timestamp>")`，页面通过 `window.EDPWidgetConfig.user`
  交给 `embed.js`；身份放在 iframe 地址的 `#` 之后，不会出现在服务器日志里。服务端校验签名和时间
  （前后 10 分钟），以 `u:<external_id>` 作为客户渠道身份：同一用户换设备、清缓存后仍是同一客户和 Room，
  坐席看到网站上的用户名。签名无效或过期返回 401，渠道未启用实名时返回 403。
- **窗口设置**：标题、欢迎语（访客打开时显示）、隐私提示（发出第一条消息前显示）。
- **服务状态**：`GET /api/v1/visitor/session` 返回会话状态、排队位置和接待坐席；Widget 顶部显示
  "正在为您转接人工客服，前面还有 N 位"或"客服 XX 正在为您服务"；AI 接待时显示"转人工"按钮
  （`POST /api/v1/visitor/handoff`，P3 接入 AI 后生效）。
- **满意度**：会话结束后 Widget 显示评价卡片（1–5 分和意见），`POST /api/v1/visitor/csat`，每个会话评价一次；
  评分显示在会话详情中（`csat`、`csat_comment`），供 M6 报表使用。
- **留言**：Widget 的"留言"页生成留言工单（`POST /api/v1/visitor/tickets`，每个访客每小时 5 条）。
- **会话续接**：路由策略新增 `resume_window_minutes`（默认 10）。会话结束后在这段时间内客户再来咨询，
  优先分配给上次接待的坐席（坐席在线且有空位时），分配事件记为 `via: previous`。
- **图片与文件**：
  - 对象存储为 S3 兼容接口，后端自己实现 SigV4 查询串预签名（`app/integrations/storage.py`，
    用 AWS 文档中的示例校验）。开发环境用 `make dev-up` 起的平台自己的 MinIO（端口 9000），与 OpenIM 自带的
    MinIO 相互独立；生产环境的选型在 M6 完成。
  - 上传：`POST /api/v1/uploads`（坐席）或 `POST /api/v1/visitor/uploads`（访客，每小时 30 个）按文件名、
    类型和大小签发 10 分钟有效的上传地址，浏览器直接 PUT 到对象存储。只允许常见图片（10 MB 以内）和
    PDF、Office、TXT、ZIP 文件（20 MB 以内）。
  - 消息里引用平台签发的文件链接 `{EDP_PUBLIC_API_URL}/api/v1/files/<key>?sig=<HMAC>`：
    打开时校验签名后 302 到 5 分钟有效的对象存储地址。链接长期有效、不暴露存储凭证；
    坐席发送附件时只接受这种链接。
  - 入库时图片、文件消息统一为 `{url, name, size, width, height, mime}`；坐席发送走平台接口
    （`type: image | file`），访客经 IM 直接发送。
- **控制台**："设置"页改为分页签，"接入渠道"中新增渠道设置抽屉：基本信息与路由策略、窗口文案、
  允许嵌入的网站、嵌入代码、实名访客密钥与签名示例代码。工作台聊天区支持发送和查看图片、文件。

### 12.2 联调发现

- OpenIM JS SDK 用 `createImageMessageByURL` / `createFileMessageByURL` 创建的消息不能用 `sendMessage` 发送：
  SDK 会尝试从本地路径重新上传，报 `Can not find target file`（10002）。文件已经在对象存储里时要用
  `sendMessageNotOss`（`im-client` 的 `sendImage` / `sendFile` 已改用它）。

### 13.2 对象存储选型

- **结论**：平台只依赖 S3 兼容接口的一个小子集——查询串预签名（SigV4）的 PUT/GET、HEAD/PUT 存储桶——
  存储服务可以替换。
  - 公有云部署：使用部署地域的云厂商对象存储（阿里云 OSS、腾讯云 COS、华为云 OBS 等，经 S3 兼容接口访问）。
    私有桶，只通过平台签发的短时 URL 访问；配置 CORS（允许控制台与 Widget 的域名直传）、生命周期规则和服务端加密。
    OSS 要求虚拟主机风格：`EDP_STORAGE_ENDPOINT` 写成带存储桶的域名，`EDP_STORAGE_BUCKET` 留空。
  - 私有化部署：推荐 SeaweedFS（Apache-2.0）；客户已有 Ceph 时可用 Ceph RGW。
  - **不在生产环境使用 MinIO 社区版**：社区版 2025 年起不再发布预编译二进制和镜像，2026 年 2 月仓库标记为不再维护
    并归档（不再有安全修复），2026 年 9 月 Docker Hub 上的 minio/minio 镜像被移除；许可证为 AGPL-3.0。
- **验证**：`tests/test_storage_contract.py` 用真实服务验证建桶、预签名上传下载（含中文、空格和括号的对象名）、
  篡改签名参数和错误密钥被拒绝；已在 MinIO（bitnamilegacy 2024.1.11）和 SeaweedFS 4.48 上通过，
  SeaweedFS 也正确响应浏览器直传所需的 CORS 预检。换用其他存储前先跑这个测试。
- **开发环境**：`make dev-up` 暂时沿用已冻结的 `bitnamilegacy/minio:2024.1.11`（已缓存的镜像可继续使用，
  可用 `EDP_MINIO_IMAGE` 替换）；计划改为 SeaweedFS（本次因 Docker Hub 限流未能拉取镜像验证 Compose 配置）。
