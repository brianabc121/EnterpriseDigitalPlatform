## 1. 目标

- **P0（多租户骨架）**：
  - 开发环境一键启动。
  - 平台可以开通租户；员工可以登录。
  - 按角色控制功能权限，按租户隔离数据（PostgreSQL RLS），按归属控制客户可见性（DataScope）。
  - 提供控制台和运营后台的骨架，CI 全绿。
- **P1（Web 客服核心）**：接入 OpenIM，完成访客 Widget、会话与路由、坐席工作台、转接与客户转移。P0 完成后再细化任务。

## 2. 工程约定

- **目录**：
  - `backend/`：FastAPI 后端。
  - `frontend/`：pnpm workspace，包含 `apps/console`、`apps/platform-admin`、`packages/api-client`。
  - `deploy/compose/`：开发环境。
- **后端**：
  - Python 3.12，用 uv 管理依赖。
  - FastAPI、SQLAlchemy 2（async + asyncpg）、Alembic。迁移手写，因为 RLS 策略要用 SQL 表达。
  - pydantic-settings（环境变量前缀 `EDP_`）、argon2-cffi、PyJWT、uuid-utils（UUIDv7）。
  - 测试用 pytest + httpx，代码检查用 ruff + mypy。
- **数据库角色**：

  | 角色 | 用途 | RLS |
  |---|---|---|
  | 所有者（开发环境为 `postgres`） | 执行迁移 | — |
  | `edp_app` | 员工请求（租户内） | 受租户隔离策略约束 |
  | `edp_platform` | 平台运营、租户开通 | 通过专用策略访问全部行 |

- **租户上下文**：
  - 每个事务开始时执行 `set_config('app.tenant_id', <租户ID>, true)`，由 SQLAlchemy 的 `after_begin` 事件自动完成。
  - RLS 策略使用 `app_current_tenant()`（等价于 `NULLIF(current_setting('app.tenant_id', true), '')::uuid`）。
  - 没有设置租户时查询返回空（fail-closed）。
- **跨租户引用**：租户表之间的外键使用 `(tenant_id, id)` 复合外键，从数据库层面禁止引用其他租户的行。
- **接口**：
  - `/api/v1/*` 面向租户员工，`/platform/v1/*` 面向平台运营。
  - 错误统一为 `{"error": {"code": "...", "message": "..."}}`。
- **令牌**：
  - 员工：Access Token（15 分钟）+ Refresh Token（7 天，httpOnly Cookie，每次刷新都轮换；检测到重复使用时吊销整组）。
  - 平台：独立密钥签发的 Access Token（2 小时）。
- **前端**：
  - Vue 3 + TypeScript + Vite + Pinia + Vue Router + Element Plus（中文）。
  - API 类型由后端导出的 `openapi.json` 经 openapi-typescript 生成，请求用 openapi-fetch。
- **提交**：每个任务独立提交，提交前本地跑通 lint 和测试。

## 7. P1 M1：OpenIM 集成（细化）

### 7.1 技术验证结论（OpenIM Server v3.8.3，2026-09-28 在开发环境实测）

- **开发环境**：
  - 官方镜像 `openim/openim-server:v3.8.3`，依赖 MongoDB 7、Redis 7、etcd 3.5、Kafka（KRaft 单节点）和 MinIO，启动约 20 秒后健康。
  - Docker Hub 上的 `minio/minio` 已无法拉取，开发环境暂用 `bitnamilegacy/minio:2024.1.11`；Kafka 用 `apache/kafka:3.9.1`。
- **发送后回调 `afterSendGroupMsg`**：
  - 在消息写入 Kafka 之后、分配 seq 之前触发，所以回调里的 seq 恒为 0，去重只能用 `serverMsgID`。
  - 通过进程内队列异步投递（2 个 worker，缓冲 100），失败不重试，因此对账是必需的，不是可选的兜底。
  - 平台自己发送的在线信令（自定义消息）也会回调，入库时要按发送者过滤。
  - REST 发送的消息 `msgFrom=200`，SDK 发送的为 100。`ex` 可以由客户端任意填写，不能作为身份依据。
- **建群**：
  - 只有管理员能建立群主为他人的群，但任何用户都能建立自己当群主的群。
  - 因此开启 `beforeCreateGroup` 回调，拒绝非平台服务群。回调里群主出现在 `initMemberList`（roleLevel=100），`ownerUserID` 字段为空。
- **对账接口**：
  - `/msg/get_conversations_has_read_and_max_seq` 批量获取会话最大 seq；`/msg/pull_msg_by_seq` 按区间拉取，`content` 为 base64。
  - 群通知（建群、进群、踢人）也占用 seq；在线信令不落库，不占 seq。
  - 最大 seq 与查询用户是否在群里无关；拉取消息时才按成员身份过滤。
- **ID 字符**：用户 ID 只接受字母、数字和下划线，含 "-"、"." 等字符时返回 1001。
- **错误码**：重复注册用户返回 1102，重复建群返回 1202，可以按"已存在"处理；未注册用户换 token 返回 1004（不是 1101）。
- **踢人**：成员会被移除，但接口可能返回 1001 "maxSeq is invalid"（被踢用户从未同步过该会话时）。M5 转接时以成员列表为准。
- **JS SDK**：`@openim/client-sdk` 3.8.3（GPL-3.0，上线前需要商业授权），可以直接在 Node 22 中运行，用于自动化测试。

### 7.2 约定

- **IM ID**（`{t}` 为 IM 前缀：租户代码中的 "-" 换成大写 "X"，因为 OpenIM 不接受 "-"；ID 为 32 位十六进制）：
  - 客户身份 `{t}_c_{身份ID}`、员工 `{t}_s_{员工ID}`、机器人 `{t}_bot`、系统用户 `{t}_sys`。
  - 服务群 `{t}_r_{RoomID}`，群主为 `{t}_sys`。
  - 前缀不含下划线，回调里按第一个下划线拆出前缀，再把 "X" 还原成 "-" 得到租户代码（租户代码只有小写字母，替换可逆）。
- **渠道 key**：`{t}.{32 位随机十六进制}`。公开嵌入客户网站，只用于识别渠道，不是凭证。
- **访客令牌**：平台签发的 JWT（独立密钥，audience `edp:visitor`，有效期 365 天），代表浏览器里的一个访客身份。令牌无效时按新访客处理。
- **回调地址**：`/hooks/openim/{共享密钥}/{command}`。OpenIM 回调不签名，所以把密钥放在路径里；部署时回调入口只对内网开放。

**联调中发现并已修复的问题**：

- **租户代码含 "-" 时无法接入**：OpenIM 的 ID 不接受 "-"。已改为 IM 前缀编码（见 §7.2），内存版 OpenIM 和契约测试都覆盖了这条规则。
- **SDK 缺陷**：`@openim/client-sdk` 3.8.3 中，没有任何会话的用户登录后，一旦收到新会话的消息，SDK 就会抛出异常，发送也随之失败。新访客、新开通的坐席都会遇到。
  - `im-client` 已加防护；SDK 内部结构变化时测试会失败。
  - 升级 SDK 时需要重新确认；建议向 OpenIM 反馈。
- **刷新后历史为空**：SDK 登录后首次同步完成之前拉取历史，会得到空列表。`im-client` 的 `connect()` 改为等同步完成后才返回。
- **回调响应被误当作放行**：OpenIM 把回调的任何 JSON 响应都当作放行。密钥错误时改为返回纯文本，使配置错误表现为拒绝。

## 9. P1 M2：会话与路由（完成情况，2026-09-28）

### 9.1 实现要点

- **进程**：API、实时消费进程（`python -m app.worker`）、调度进程（`python -m app.scheduler`）。
  三者共用 `AppContext`（数据库、Redis、OpenIM 客户端、事件总线）。
- **事件流**：Redis Streams，按 Room 哈希到 8 个分区。
  - 每个分区由持有租约的一个消费者顺序处理，同一个 Room 的事件严格有序；可以运行多个消费进程。
  - 新的租约持有者先接管前任留下的未确认事件，再读新事件。
  - 处理失败重试 3 次，仍失败写入死信流 `edp:events:dead`，不阻塞分区。
  - 回调和对账入库的新消息发布 `message.received`；发布失败的由调度进程每 30 秒补发。
- **会话引擎**（设计 §8.2、§11.3）：
  - 客户的第一条消息开启会话，按渠道绑定的路由策略（没有绑定时用默认策略）进入排队。
  - 分配顺序：归属坐席优先 → 技能组（会话或策略的默认技能组；都没有时在全部坐席中分配）
    → 负载率（当前会话数 / 并发上限）最低 → 最久未分配。按租户加咨询锁，不会超过并发上限。
  - 分配后把坐席拉进服务群，给客户发"客服 XX 为您服务"，给坐席发 `session.assigned` 信令；
    没能立即分配时告知排队位置。
  - 结束会话时给客户发结束提示，把坐席移出服务群；空出的名额立即分给排队中的会话。
  - 调度进程每 10 秒：心跳超过 90 秒的坐席下线，其未回复过的会话退回队列（重新计时，优先级 +1）；
    排队超过 `max_wait_seconds` 转为留言；人工接待超过 `idle_close_minutes` 没有新消息则结束。
  - 非工作时间的消息直接转为留言（同一段时间内的后续消息追加到同一条留言）。
  - 所有状态变化写入 `session_events`。
- **IM 发件箱（`im_ops`）**：拉人、踢人、客户提示、坐席信令与会话状态在同一个事务里写入，
  提交后立即执行；同一个 Room 按写入顺序执行，失败的按指数退避重试（调度进程每 5 秒），
  信令失败不重试。这样 OpenIM 短暂不可用时，状态与 IM 最终一致。
- **调度进程选主**：用 Redis 租约保证只有一个实例执行周期任务（M1 后续事项"调度进程单实例"已完成）。
- **数据范围**：
  - 客户：归属自己的客户 + 当前有会话分配给自己的客户（会话结束后不再可见）；
    主管另可看到所带技能组组员名下和正在接待的客户。
  - 会话：分配给自己的、自己名下客户的；主管另可看到所带技能组及组员的会话。
- **接口**：技能组、路由策略（含工作时间校验）、渠道绑定策略、坐席看板与并发、
  坐席接待状态 / 心跳 / IM 令牌、会话列表 / 详情 / 结束、留言列表 / 完成。

## 10. P1 M4：坐席工作台（完成情况，2026-09-28）

### 10.1 联调发现：OpenIM 实时推送的两个问题

浏览器验收一开始只有约一半的运行通过：访客偶尔收不到"客服 XX 为您服务"，坐席偶尔收不到分配信令。
排查 OpenIM 源码和日志后确认是两个问题：

1. **离线推送拖慢在线推送**。默认配置启用了个推（Getui）却没有凭证。推送服务按 Kafka 分区顺序处理消息，
   每次给离线用户（例如已经关掉浏览器的坐席）推送，都要等一次失败的外部 HTTP 请求，排在后面的在线推送随之延迟。
   开发环境已关闭离线推送（`IMENV_OPENIM_PUSH_ENABLE=none`）。平台是 Web 端，不需要手机离线推送；
   以后接入 App 时再配置推送供应商，并单独评估推送服务的吞吐。
2. **刚连上的用户收不到推送**。msggateway 每秒批量上报一次用户上线，推送服务要过一两秒才知道这个用户在线。
   这段时间里发给他的在线信令直接丢弃，群消息也不推送；JS SDK 不检测 seq 缺口，之后也不会补拉。
   处理方式是把平台接口作为消息的准绳，IM 只负责低延迟：
   - Widget：连上后、之后页面可见时每 10 秒、以及重连后，用访客接口（`GET /api/v1/visitor/messages`）补齐，
     按 IM 消息 ID 与 IM 推送去重。
   - 工作台：先连 IM，等 2 秒再上线接单；会话列表和当前会话每 10 秒以接口为准刷新一次，重连后立即刷新。

修复后，M4 浏览器验收连续 5 次全部通过。

## 12. P1 M3：访客 Widget（完成情况，2026-09-28）

### 12.1 实现要点

- **嵌入**：`embed.js`（Widget 的 `public/` 下）在页面右下角放一个"在线客服"按钮，点开时显示 iframe 里的 Widget。
  父页面与 iframe 之间用 postMessage 通信，双方都校验来源：`edp:open` / `edp:hidden`（显示状态）、
  `edp:unread`（收起时收到的新消息数，显示为按钮角标）、`edp:close`（Widget 里的收起按钮）。
  iframe 默认隐藏但照常连接 IM，所以收起时也能收到消息和提醒。
- **允许嵌入的网站**（渠道设置 `allowed_origins`）：Widget 取父页面来源（`location.ancestorOrigins`，
  不支持时用 referrer）随初始化请求上报，不在列表中的返回 403"当前网站未被授权接入在线客服"；
  列表为空表示不限制；Widget 自己的地址（`EDP_WIDGET_PUBLIC_URL`，例如访客测试页）总是允许。
  这一校验用于防止别人随手把客服窗口挂到自己的网站上，不是安全边界：来源由浏览器上报，脚本可以伪造请求。
  访客身份的可信度只来自下面的签名。
- **实名访客**：渠道启用后生成签名密钥（`POST /api/v1/channels/{id}/identity-secret`，可更换）。
  网站后端计算 `HMAC-SHA256(密钥, "<external_id>:<name>:<timestamp>")`，页面通过 `window.EDPWidgetConfig.user`
  交给 `embed.js`；身份放在 iframe 地址的 `#` 之后，不会出现在服务器日志里。服务端校验签名和时间
  （前后 10 分钟），以 `u:<external_id>` 作为客户渠道身份：同一用户换设备、清缓存后仍是同一客户和 Room，
  坐席看到网站上的用户名。签名无效或过期返回 401，渠道未启用实名时返回 403。
- **窗口设置**：标题、欢迎语（访客打开时显示）、隐私提示（发出第一条消息前显示）。
- **服务状态**：`GET /api/v1/visitor/session` 返回会话状态、排队位置和接待坐席；Widget 顶部显示
  "正在为您转接人工客服，前面还有 N 位"或"客服 XX 正在为您服务"；AI 接待时显示"转人工"按钮
  （`POST /api/v1/visitor/handoff`，P3 接入 AI 后生效）。
- **满意度**：会话结束后 Widget 显示评价卡片（1–5 分和意见），`POST /api/v1/visitor/csat`，每个会话评价一次；
  评分显示在会话详情中（`csat`、`csat_comment`），供 M6 报表使用。
- **留言**：Widget 的"留言"页生成留言工单（`POST /api/v1/visitor/tickets`，每个访客每小时 5 条）。
- **会话续接**：路由策略新增 `resume_window_minutes`（默认 10）。会话结束后在这段时间内客户再来咨询，
  优先分配给上次接待的坐席（坐席在线且有空位时），分配事件记为 `via: previous`。
- **图片与文件**：
  - 对象存储为 S3 兼容接口，后端自己实现 SigV4 查询串预签名（`app/integrations/storage.py`，
    用 AWS 文档中的示例校验）。开发环境用 `make dev-up` 起的平台自己的 MinIO（端口 9000），与 OpenIM 自带的
    MinIO 相互独立；生产环境的选型在 M6 完成。
  - 上传：`POST /api/v1/uploads`（坐席）或 `POST /api/v1/visitor/uploads`（访客，每小时 30 个）按文件名、
    类型和大小签发 10 分钟有效的上传地址，浏览器直接 PUT 到对象存储。只允许常见图片（10 MB 以内）和
    PDF、Office、TXT、ZIP 文件（20 MB 以内）。

### 13.2 对象存储选型

- **结论**：平台只依赖 S3 兼容接口的一个小子集——查询串预签名（SigV4）的 PUT/GET、HEAD/PUT 存储桶——
  存储服务可以替换。
  - 公有云部署：使用部署地域的云厂商对象存储（阿里云 OSS、腾讯云 COS、华为云 OBS 等，经 S3 兼容接口访问）。
    私有桶，只通过平台签发的短时 URL 访问；配置 CORS（允许控制台与 Widget 的域名直传）、生命周期规则和服务端加密。
    OSS 要求虚拟主机风格：`EDP_STORAGE_ENDPOINT` 写成带存储桶的域名，`EDP_STORAGE_BUCKET` 留空。
  - 私有化部署：推荐 SeaweedFS（Apache-2.0）；客户已有 Ceph 时可用 Ceph RGW。
  - **不在生产环境使用 MinIO 社区版**：社区版 2025 年起不再发布预编译二进制和镜像，2026 年 2 月仓库标记为不再维护
    并归档（不再有安全修复），2026 年 9 月 Docker Hub 上的 minio/minio 镜像被移除；许可证为 AGPL-3.0。
- **验证**：`tests/test_storage_contract.py` 用真实服务验证建桶、预签名上传下载（含中文、空格和括号的对象名）、
  篡改签名参数和错误密钥被拒绝；已在 MinIO（bitnamilegacy 2024.1.11）和 SeaweedFS 4.48 上通过，
  SeaweedFS 也正确响应浏览器直传所需的 CORS 预检。换用其他存储前先跑这个测试。
- **开发环境**：`make dev-up` 暂时沿用已冻结的 `bitnamilegacy/minio:2024.1.11`（已缓存的镜像可继续使用，

  - 每次调用记入 `llm_calls`（场景、供应商、模型、tokens、耗时、成败），在独立事务里写，调用失败也有记录。

  - 条目为问答（标准问、相似问、答案）或文档（标题、正文）；草稿 → 发布 → 下架，已发布的内容修改后立即生效、
    版本号加一（内容真正改变时）；可见范围：对客（AI 与坐席）、仅坐席、仅管理员；有效期；分类与标签；引用次数。
  - 发布时生成检索单元：问答的每个问法一条，文档按 500 字切片（60 字重叠，带标题前缀）；关键词为中文二元组
    （去掉"请问""你好"之类的口头语）加英文与数字词，GIN 索引；向量为 pgvector HNSW 余弦索引。
  - 检索：语义与关键词两路各取候选，RRF 融合，每个条目取最相关的一段；相关度低于 0.3 的不返回；
    租户、状态、可见范围、有效期的过滤全部在 SQL 里完成。
  - CSV 批量导入（标准问、答案、相似问、分类）；检索测试；`python -m app.cli kb-reindex [--tenant]`
    更换向量模型后重建检索单元。
- **AI 接待与转人工**（设计 §11.1、§11.2）：
  - 路由策略为"AI 优先"、租户启用了 AI、平台配置了大模型且本月额度未用完时，新会话由 AI 接待（`ai_serving`），
    不受工作时间限制；否则按原规则排队，AI 不能接待的原因（额度用完、未启用等）记为会话的转人工原因。
  - 客户连续发的消息等 2 秒（`EDP_AI_DEBOUNCE_SECONDS`）合并后回复。实时消费进程每 0.5 秒领取到期的会话
    （`FOR UPDATE SKIP LOCKED`，2 分钟租约，进程退出后自动重试），分读取、判定、写入三步，调用模型时不占数据库事务；
    写入前再确认会话仍由 AI 接待（访客可能刚点了转人工）。
  - 判定流程：前置规则（客户要求人工、敏感诉求、VIP 标签 → 立即转人工，不调用模型）→ 检索对客知识 →
    模型按资料回答并给出把握和是否需要人工 → 后置护栏（回复为空、过长、资料里没有的承诺类话术、敏感词：
    第一次改发兜底话术，连续两次转人工）→ 软信号加权（知识相关度低 0.4、模型把握低 0.3、负面情绪 0.3、
    重复提问 0.3、否定回答 0.2、轮数过多 0.2），得分达到阈值（默认 0.6）转人工。模型不可用时直接转人工。
  - 每轮判定写入 `ai_decisions`（问题、回复、依据的知识与相关度、各项信号与得分、转人工原因），

  - 转人工：用快速模型写交接摘要（诉求、已提供的信息、已答复的内容、情绪；模型不可用时取最近的客户消息），
    工作时间内进入排队并分配，非工作时间生成留言（带原因和摘要）并结束会话。
  - AI 接待中的会话空闲超时后以"AI 解决"结束。
  - AI 回复经发件箱以机器人身份发到服务群（名称为租户设置的名称，扩展字段标记 AI），与系统提示一样按 Room 顺序发送。

    接待中的会话下一轮转人工。

## 15. P4：知识沉淀闭环（完成情况，2026-09-29）

### 15.1 实现要点

- **从会话提炼**（设计 §12.3、§12.4，`app/modules/kb/extraction.py`）：
  - 调度进程每小时处理最近 7 天结束、还没提炼过的会话（`python -m app.cli kb-extract [--tenant]` 立即运行）；
    只挑有人工参与、因知识缺失转人工（模型判断或把握不足）或客户评价 4 分及以上的会话。
    每个会话只提炼一次，失败的最多重试 3 次（`kb_extractions`）。
  - 预处理：去掉系统提示和寒暄（你好、谢谢、好的等整句），合并同一方连续的消息，**先脱敏再提炼**；
    模型输出里含个人信息占位符、不可泛化或把握低于 0.6 的问答丢弃（三道关口的前两道，第三道是审核）。
  - 与已有知识比对（检索相关度 ≥ 0.8 视为同一问题）：答案一致（新答案没有出现旧答案里没有的数字、
    没有相反的否定说法）→ 相似问法（问法已存在则忽略）；不一致 → 答案冲突；否则 → 新问题；
    客服没有解答的问题 → 知识缺口（已有知识能回答的不算）。
  - 同种类、同目标知识的待审候选按问题相似度（词项 Jaccard ≥ 0.6）聚类：出现次数加一、补充证据（最多 10 段），
    保留把握更高的答案。候选记录提炼模型和提示词版本；只在同一租户内比对和聚类。
- **审核台**（设计 §12.5，`/knowledge` → 审核台，查看需要 `kb:manage`、处理需要 `kb:publish`）：
  - 按出现次数、最近出现时间排序，显示近 7 天次数；按类型筛选（缺口即"知识缺口榜"），可查看已处理的记录。
  - 详情：可编辑的问题与答案、客户的其他问法、冲突时新旧答案的逐字差异、相似的已有知识（可"合并到这条"）、
    脱敏后的证据对话、提炼模型与提示词版本。
  - 操作：通过（新问题、缺口新建为问答并发布，可设为仅坐席可见；相似问法并入原问答；冲突用新答案更新原问答）、
    合并到选定的知识、驳回（必须填写理由）。处理结果写入审计日志。
  - 自动合并（AI 接待设置里开启，默认关闭）：只适用于相似问法，证据 ≥ 3 条且相关度 ≥ 0.85。
- **版本管理**：每次发布（首次发布、修改、合并、回滚）保存内容快照（`kb_item_versions`），下线期间改过内容再发布时
  版本号加一；版本历史里可以把任意历史版本恢复为新版本。有效期到期的知识由调度进程自动下线。
- **分发给坐席**（设计 §12.6）：
  - 知识动态：工作台右侧"动态"页签列出最近发布、更新的知识（只含坐席能用的），每分钟刷新；
    会话面板不再依赖是否选中会话。
  - 必读：知识可设为必读，发布或更新后坐席需要确认已读（按版本记录，更新后重新确认）；"动态"页签显示待确认数，
    管理员在知识详情里看到确认情况（有接待权限的在职员工）。
  - 知识周报：每周一生成上一周的周报（新增、更新、到期下线、AI 引用最多、知识缺口 Top 10、审核情况、AI 接待效果），
    知识库页"周报"查看，管理员可以随时生成本周的（`kb-digest` 命令同样可以）。企业微信推送在 P2 接入。
- **运营指标**（设计 §12.7，知识库页"运营数据"）：知识命中率、AI 转人工原因分布、待处理缺口与平均处理时长、
  候选通过率、AI 建议采纳率（坐席发送时标明来源：手写、快捷话术、AI 建议、知识检索）、长期未命中的知识、
  AI 引用最多和评价为"没用"最多的知识。坐席在工作台检索知识时可以评价"有用 / 没用"。

## 16. P2：企业微信（完成情况，2026-09-29）

只用官方接口，以服务商身份通过代开发应用接入（设计 D4、§3.1、§7.4、§10.3–§10.5）。没有服务商资质，
全部功能按官方文档实现，并在模拟企业微信服务（`backend/tests/fake_wecom.py`）上验证；真实联调见 16.3。

### 16.1 实现要点

- **回调加解密**（`app/integrations/wecom/crypto.py`）：与官方 WXBizMsgCrypt 一致（AES-256-CBC、按 32 字节
  PKCS#7 填充、SHA1 签名、ReceiveId 校验），用官方文档的示例数据验证；XML 拒绝 DOCTYPE 和实体声明。
- **服务端接口**（`app/integrations/wecom/client.py`）：suite_ticket（每 10 分钟推送）存 Redis；
  suite_access_token、授权企业的 access_token（代开发应用用永久授权码 gettoken）和 JS-SDK ticket 按有效期
  缓存在 Redis，多个进程共用，凭证失效类错误换新凭证重试一次；网络故障和"系统繁忙"作为可重试错误。
- **授权**（`app/modules/wecom/auth.py`，控制台"企业微信"页）：管理员点"扫码授权企业微信"，平台用预授权码
  生成授权链接，state 记住发起的租户（企业微信要求 state 只含字母和数字，租户信息放在 Redis）。
  浏览器跳回和 create_auth 回调都能完成绑定（按 state 加锁，临时授权码只能用一次，先到的一方绑定失败时后到的
  一方给出同样的原因）；永久授权码加密保存（`EDP_DATA_ENCRYPTION_KEY`，Fernet，密文带版本前缀，将来可换成
  租户级信封加密）；一个企业只能绑定一个租户。授权后全量同步。也处理 change_auth、cancel_auth（停用渠道，
  保留客户和消息）和 reset_permanent_code；管理员可以解除绑定。
- **回调路由**（`/hooks/wecom/cmd`、`/hooks/wecom/data`）：验签解密后，服务商事件在请求内处理；企业的事件按
  CorpID 找到租户写入事件流，立即应答，由实时消费进程处理（微信客服按客服账号、其余按企业串行）。
  企业微信对不同应用形态的推送位置不完全一致，两个入口按事件内容统一分发；ReceiveId 必须与事件里的企业一致。
- **微信客服**（`app/modules/wecom/kf.py`）：
  - 每个交给应用管理的客服账号是一个渠道（`wecom_kf`），沿用路由策略、AI 接待、排队分配、会话记录、报表。
  - 入站：回调只带 10 分钟有效的 token，按客服账号串行调用 sync_msg，每页连同游标一起提交；回调丢失时调度进程
    每 5 分钟兜底拉取。按 msgid 去重（`messages.ext_msg_id`）；授权前的历史消息不导入。新客户用 batchget 取昵称、
    头像、unionid，同一企业的外部联系人或 unionid 相同的客户归到同一份档案。图片、语音、视频、文件立即转存到
    对象存储（临时素材 3 天后失效）。新接入的会话置为"由智能助手接待"（1），不转为人工接待（3）。
  - 平台消息库为准：入站消息先入库、发布 message.received，再以客户身份镜像到服务群（坐席工作台实时看到）；
    提示、AI 回复、坐席回复先写入消息库，投递到企业微信成功后再镜像。发件箱对这类 Room 分"渠道投递"和
    "IM 操作"两条通道，每步单独提交：OpenIM 不可用时客户照常收到回复，镜像恢复后按顺序补上。
  - 回复窗口：客户最后一次发消息后 48 小时内最多 5 条（`GET /sessions/{id}/reply-window`），坐席发送前检查、
    投递时再检查；工作台显示"剩余 N 条 / 截止 hh:mm"，用完后输入框禁用并说明原因；欢迎语不占额度。
    投递失败（包括 msg_send_fail 事件）的原因记在消息上，工作台可见。
  - 客户进入会话（enter_session）时，用 welcome_code 发送客服账号的欢迎语（"设置 → 接入渠道"里设置）。
  - AI 回复加"【AI】"前缀（纯文本渠道的 AI 生成内容标识，设计 §3.3）；文本按 2048 字节截断。
  - 混合模式：接待人员在企业微信客户端直接回复的消息（origin=5）只归档。
- **客户联系与客户群**（`app/modules/wecom/contacts.py`）：
  - 成员：user/list_id 同步成员，姓名用 user/get 补齐；管理员在"成员绑定"里把成员绑定到平台员工
    （`staff.wecom_userid`），员工也可以扫码自行绑定。
  - 客户：按配置了客户联系的成员全量同步（batch/get_by_user），之后按 change_external_contact 回调增量更新；
    客户档案名优先用备注名；客户没有归属坐席时，最早添加他的已绑定员工成为归属坐席（归属记录原因为
    "企业微信添加人"）。
  - 标签：企业标签以企业微信为准（各添加人的并集），平台上打的企业标签写回企业微信（mark_tag），平台自有标签不受影响。
  - 新客户欢迎语：add_external_contact 回调带 WelcomeCode 时发送，可附带微信客服链接（AI 客服入口），默认关闭。
  - 客户群：同步群列表和成员，外部成员关联客户档案；change_external_chat 回调增量更新或标记解散。
  - 在职继承：转移客户（批量转移、离职交接）时勾选"同时变更企业微信里的添加人"，按（原添加人，接替人）分批
    调用 transfer_customer；调度进程每小时回收结果（`transfer_result`），归属记录显示"企业微信等待接替 / 已接替 /
    接替失败"。原归属坐席或新归属坐席没有绑定成员、客户不是原坐席添加的，都跳过。
- **应用消息**（`app/modules/wecom/notify.py`）：新会话分配、转接请求、必读知识发布、知识周报推送给绑定了成员的
  员工（文本卡片），链接经网页授权免登进入控制台；租户可以关闭提醒。
- **登录**：登录页"企业微信扫码登录"（CorpApp 扫码登录，state 由控制台生成并核对）；企业微信内打开控制台页面
  时网页授权免登（`GET /api/v1/auth/wecom/oauth`）；两者都回到 `/wecom/login`，用 code 换取成员身份后登录绑定的员工。
- **聊天工具栏侧边栏**（`/wecom/sidebar?corp=<CorpID>`，移动端布局）：JS-SDK 注入企业与应用权限（`GET
  /api/v1/wecom/jssdk-config`），取当前客户或客户群；显示客户档案、标签、企业微信添加人、最近会话摘要；员工粘贴
  客户的问题获取 AI 建议（结合客户在微信客服和网页的历史），一键 sendChatMessage 发送并记入平台
  （`wecom_sidebar_messages`）。数据范围双重校验：员工能看到的客户，或企业微信里员工自己添加的客户。
- **控制台**："企业微信"页（授权、同步情况、微信客服账号与欢迎语、成员绑定、欢迎语与提醒设置、解除绑定）；
  工作台回复窗口与失败原因；客户面板显示企业微信信息（添加人、标签、客户群、在职继承）；转移客户的"同步企业微信"。
- **命令**：`python -m app.cli wecom-sync [--tenant]`（立即全量同步并拉取微信客服消息）、`wecom-transfers`
  （立即回收在职继承结果）。

### 17.1 G1：企业微信补齐

- **离职继承与客户群继承**（迁移 `0012`）：

    `wecom_transfers.kind` 记录方式，结果回收按方式调用 `transfer_result` 或 `resigned/transfer_result`。
  - "离职继承"页读取 `get_unassigned_list`（企业微信里待分配的离职成员客户，关联平台客户档案），分配给绑定了
    企业微信的员工：平台归属变更（记归属历史）+ 离职继承，可同时转移他的客户群。

    `groupchat/onjob_transfer`（每次最多 100 个群、结果同步返回，记在 `wecom_group_transfers`）；接手方是技能组时
    轮流分配给组员。
- **客户群活码**：`groupchat/add_join_way`（scene=2）生成"加入群聊"二维码，可以设置群满后自动建群（群名前缀和
  起始序号）；二维码带 `edp` 开头的 state，客户经它进群后群成员详情带同样的 state（`wecom_group_members.state`），
  据此统计进群人数。
- **一键建群**：侧边栏在客户单聊里调用 JS-SDK `openEnterpriseChat`（拉上接单员），员工在企业微信里确认后把
  新群 ID 交给平台（`POST /api/v1/sidebar/groups`），平台立即同步这个群并关联客户档案（记审计）。
- **群发任务**（`broadcast:manage`，租户管理员和主管）：发给客户时按标签、归属坐席筛选可见范围内的客户，每位
  客户由归属坐席绑定的成员（没有时由最早添加他的成员）发送，按发送成员分别调用 `add_msg_template`；发到客户群时
  按群或群主筛选（主管只能发到自己或组员作为群主的群）。调度进程每 30 分钟用 `get_groupmsg_task`、
  `get_groupmsg_send_result` 回收结果，详情里可以立即刷新、提醒（`remind_groupmsg_send`）、停止
  （`cancel_groupmsg_send`）。
- **侧边栏**：客户标签可以修改（企业标签写回企业微信，数据范围同侧边栏：可见的客户或自己添加的客户），
  增加快捷话术与知识检索；发出的内容带上员工粘贴的客户问题，一问一答进入知识沉淀流水线（候选来源记为
  sidebar）。JS-SDK 脚本地址可以用 `VITE_WECOM_JSSDK_URLS` 换成模拟服务（`/jssdk/jwxwork.js`），浏览器验收走真实的
  JS-SDK 调用路径。
- **手机版工作台**：`/m` 路由，企业微信手机端打开工作台时自动进入；与电脑版共用工作台状态、IM 连接和聊天面板，
  一次显示一屏（会话列表 → 聊天 → 客户资料/知识检索抽屉）。
- **微信客服菜单消息**：AI 的回答带「转人工」按钮，人工接待过的会话结束提示带 5 档满意度按钮（与提示合并成
  一条，节省额度；起始文本超过 1024 字节时发普通文本）。客户点选产生一条带 `menu_id` 的客户消息：转人工直接
  请求人工；满意度记在刚结束的会话上（24 小时内，记 `csat` 事件）并回复"感谢您的评价"，不开始新会话。

- **语音**：微信客服语音下载后转写（`EDP_ASR_*`，OpenAI 兼容 `/audio/transcriptions`），转写文字作为消息的纯文本
  供 AI 与知识提炼使用；AMR 用 ffmpeg 转成 MP3（找不到 ffmpeg 时保留原文件）。工作台播放语音并显示转写文字。

  审核台（来源记为 zone）；客户 360 和侧边栏的客户群显示最近的摘要与情绪。专区程序本身、可用模型与费用待 POC。

### 17.3 G3：权限、合规与审计

- **租户数据密钥**（迁移 `0014`，`app/modules/security`）：每个租户一把随机数据密钥（Fernet），用主密钥
  （`EDP_DATA_ENCRYPTION_KEY` 派生）包装后存在 `tenant_keys`，第一次加密时生成；密文格式 `v2:<版本>:<密文>`，
  早期的 `v1:`（直接用主密钥）仍可解密。企业微信永久授权码、租户自带的模型密钥、客户手机号和邮箱改用租户密钥；
  平台级密文（运营账号的 TOTP 密钥、平台模型供应商密钥）仍用主密钥。进程内缓存解开的密钥（60 秒刷新）。
  - 轮换：运营后台"数据密钥"生成新版本并把该租户现有密文换成新版本加密（旧版本保留），记审计；显示还没有换版本的
    密文数量。更换主密钥：`app.cli rewrap-keys --old-key-env <变量名>` 用旧主密钥解开各租户的数据密钥再用新主密钥
    包装，平台级密文重新加密，早期的 v1 租户密文换成租户密钥加密（可以重复执行）。
  - 加密擦除：注销删除数据时 `tenant_keys` 随租户表一起删除，备份里残留的密文无法解密；租户数据导出里客户手机号、
    邮箱导出明文（盲索引不导出，密钥表不导出）。
- **客户敏感字段**：`customers` 新增 `phone_enc`、`email_enc`、`company` 与盲索引 `phone_hash`、`email_hash`
  （HMAC-SHA256，密钥从第一版数据密钥派生，轮换不影响；手机号去掉空格、横线和 +86，邮箱转小写）。列表、详情只
  返回掩码（`138****1234`、`z***@example.com`）；`GET /api/v1/customers/{id}/sensitive` 需要新权限点
  `customer:view_sensitive` 且客户在数据范围内，每次查看写 `customer.view_sensitive` 审计。客户列表 `q` 参数：
  名称、公司模糊匹配，手机号、邮箱完整匹配。企业微信同步时补上员工备注的手机号（`remark_mobiles`）和企业名称。
- **员工与角色**（`app/modules/iam/manage.py`）：`PATCH /api/v1/staff/{id}` 修改姓名、角色、状态；停用时吊销
  刷新令牌（访问令牌在下一次请求时失效）、坐席下线、接待中的会话（包括已回复的）退回队列、OpenIM 强制下线
  （`/auth/force_logout`）；不能停用自己、至少保留一名启用的租户管理员、启用时检查坐席额度、不能管理权限高于
  自己的员工或分配超出自己权限的角色。`POST /api/v1/staff/{id}/password` 重置密码（现有登录失效）；
  `POST /api/v1/me/password` 修改自己的密码（验证当前密码，每人 15 分钟 10 次，其他登录失效并换发令牌）。
  自定义角色 `POST/PATCH/DELETE /api/v1/roles`（权限不超过自己，系统角色只读，有员工使用时不能删除），
